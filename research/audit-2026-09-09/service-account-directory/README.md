## Behavior

Service-account settings previously fetched every account, issued a separate token-count query for each, and loaded every key with its full scope document. The modal displayed only scope counts. The populated database has one service account and three keys; scaling checks use disposable 126-account/126-key fixtures, including keys scoped to 126 projects.

Account search now filters name/email before SQL count/windows and aggregates token counts once for the returned account IDs. Counts include expired keys, matching the existing contract. Direct account reads keep off-page dialogs reachable. REST account reads support an optional limit while preserving complete no-parameter responses. The service-account MCP tool now uses the shared default limit of 25, maximum 100, with search and offset; it no longer performs one count per account.

`GET /service-accounts/{id}/keys/directory` returns 50-row windows by default with a maximum of 200. Search matches name/prefix before count/paging. Rows include timestamps, restricted/full status and SQL-computed global/project scope counts; they omit token hashes and complete scope documents. Stable ID tie-breakers prevent duplicate/missing rows when names or creation times tie. Inactive accounts and expired keys remain visible. Existing complete key reads remain compatible.

The existing global-management read gate is preserved for account/key directories and direct account lookup. Create/update/revoke retain their distinct API permissions; minting still requires a browser session. A browser check exposed a separate vocabulary gate: a manager without issue readership could not load permission choices for a restricted key. Global role-create/role-update/service-account-update authority can now read the static permission vocabulary through credential-aware checks. This does not grant account data readership or credential delegation. Ordinary vocabulary readers retain the member floor; empty-scope admin keys remain refused.

The account page and `ServiceAccountKeysModal` use 50-row search windows, explicit retry states and direct detail resolution. Creation opens the new account even under an unmatched search. Key search, paging, revocation and renamed account detail preserve unfinished mint forms; transient detail errors retain the draft. Last-page revocation recovers automatically. Mint/revoke share entity invalidation, replacing duplicate handwritten key-query invalidations. Account/key metadata includes user/member and role/team/group changes. Restricted mode still requires atoms and full authority remains explicit.
