# Project access windows and explicit key authority — RADD-1115

Project access now uses stable 50-row SQL grant windows, bounded permission-safe name hydration and lazy person/team/group/role choices. The common `auth/scoped_grants.py` reader and `ScopedAccessPanel`/`GrantScopedRoleDialog` serve both project and wiki scopes, preserving separate authorization gates and wire identities. Expired grants and inactive-account labels remain visible. Individual writes preserve off-page rows.

The legacy project-grant read previously required membership somewhere, allowing a member to enumerate grants for a hidden project ID. Both the legacy and paged readers now use the public project visibility decision, including qualified relationships and credential narrowing. Hidden and missing projects return 404. Delegated create/delete retain their project member permissions and role-coverage checks; global role.update remains sufficient for grant mutations. Revoke-only actors now have the Access tab and sidebar Settings link. The settings landing route chooses the first permitted section rather than always sending them to Workflow.

The service-key form previously ignored a selected project when permissions were empty and sent `scopes: null`, minting full account authority. Restricted keys now require at least one permission. Full authority is an explicit mode; choosing it shows that current and future account permissions apply. Project selection is lazy and bounded, and clearing it retains the selected global permission restriction. The existing API's null/global/project scope contracts are unchanged. Revoke failures are visible.
