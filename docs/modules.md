# Module map

How the server is assembled and how modules connect. **Update this file in the same change that adds a module, event type, or cross-module dependency.**

## Kernel (spec 93 — `radd/kernel/`)

The kernel is the generic machinery every feature (plugin) builds on; it never disables (docs/plugin-platform.md §1). It holds the **plugin contract** (`kernel/plugin.py` — `RaddPlugin`, a manifest of contributions that evolves the pre-kernel `RaddModule`; all 49 builtin plugins construct `RaddPlugin` directly, and the migration is finished — the `RaddModule`/`load_modules` aliases are deleted), the **contribution registries** (`kernel/registry.py` — one dict per contribution kind: `entities`, `event_types`, `permissions`, `crud_resources`, `capabilities`, `tasks`, `consumers`, `integrations`, `nav`; populated by the loader, read blind by exactly one generic consumer each), the **loader/lifecycle** (`kernel/loader.py` — `load_plugins` aggregates contributions, checks `depends_on` + semver `api_version` compat; `import_models` unchanged), and the **contribution specs** (`kernel/specs.py` — `EventTypeSpec`/`CapabilitySpec`/`PermissionSpec`/`CrudResourceSpec`/`EntitySpec`/`TaskSpec`/`IntegrationSpec`/`NavItemSpec`/`PluginUiManifest`, all pure — the kernel imports nothing from `radd.modules.*`). The `radd/module.py` shim is deleted — import the contract from `radd.kernel`. The generic-mechanism modules (`events`, `access`, `auth`-core, `settings`) physically stay under `radd.modules.*` for import stability but are kernel-governed. Core-invariants: `tests/test_kernel.py`.

**The manifest REFUSES a bare value where a tuple is declared (RADD-756).** Every contribution field on `RaddPlugin` is a `tuple[Spec, ...]`, and `on_startup=_startup` instead of `on_startup=(_startup,)` is a defect Python will not catch — the dataclass stores whatever it is handed and the failure surfaces wherever the field is finally iterated. That shipped once, in 0.8.0, as an image that could not complete `lifespan`, with 1391 green tests behind it. `__post_init__` now raises for all 26 such fields, derived from the annotations rather than listed by hand, so a contribution added later is covered the day it is declared. It REJECTS rather than normalising: two valid shapes for one field is how the next module learns the wrong one. It also catches `depends_on="items"`, which is worse than a crash — a `str` is iterable, so that one fails silently as five one-character plugin names. `tests/test_app_startup.py` runs the real `create_app` lifespan, which nothing in the suite had ever done.

**`ContributionSource` (RADD-748)** records which plugin registered a contribution, kept beside the specs rather than on them: a spec is authored BY the plugin, so a self-declared `source` could disagree with reality, and only the registry is in a position to know. `page_extension_sources` is the first adopter; unregister drops the source with the spec, or a stale one outlives it and mislabels the next contribution reusing the name.

## Assembly

`radd.app:create_app()` reads `settings.modules` (ordered dotted paths), imports each package's `plugin: RaddPlugin`, verifies `depends_on`, then:

- mounts every router under `/api/v1`
- registers module `exception_handlers`
- runs module `on_startup` hooks in the lifespan
- applies `openapi_augmentors` on every OpenAPI render (this is how dynamic schema stays live)

`RaddPlugin` (see `radd/kernel/plugin.py`) is the plugin contract. Alembic discovers models the same way (`import_models(settings.modules)`), so a module's tables migrate iff the module is enabled.

**Frontend UI manifest (spec 93 / A7, chokepoint 3):** `GET /capabilities` now returns a backend-assembled UI manifest — `capabilities` (the status flags) + `nav` (plugin-contributed nav items from `registries.nav`, each with `requires` atoms / `capability` gate / `order`). The SPA sidebar (`web/src/components/shell/Sidebar.tsx`) fetches `capabilitiesQuery` and renders the plugin nav (`pluginNav`, filtered by the user's atoms + enabled capabilities) alongside its builtin nav — so an enabled plugin's nav lights up with no edit to the shell. Additive over the existing hardcoded nav (full manifest-driven replacement of `SETTINGS_NAV`/router + generic plugin pages via declarative-UI/federation are the §8b follow-up).

**Frontend module federation (spec 94, §8b-A):** the SPA is a real plugin platform — a plugin ships its own built ESM bundle that a *running* Radd loads at runtime, with zero host imports. Mechanism (native ES modules, no MF plugin): the host (`web/index.html`) declares an **import map** for the shared singletons (`react`, `react-dom[/client]`, `react/jsx-runtime`, `@tanstack/react-query`+`react-router`, `@radd/plugin-sdk`) → `/shared/*.js` shim files (generated by `web/scripts/gen-shared-shims.mjs`) that re-export the host's singletons published on `globalThis.__RADD_SHARED__` (`web/src/shared-runtime.ts`); a plugin **remote** is a Vite lib build that EXTERNALIZES those ids (keeping the bare specifiers the import map resolves) and `export default definePlugin({activate})`. The public **`@radd/plugin-sdk`** (`web/packages/plugin-sdk`) is the only frontend surface a plugin imports: the **slot registry** (`registerSlot`/`unregisterPlugin`/`useSlot`/`<Slot>`, ids `issue.panel.section`/`issue.tab`/`sidebar.nav`/`route.page`/`settings.page`/`dashboard.widget`/`item.action`), theme **tokens** (semantic `--radd-*` over the host zinc scale) + **primitives** (Button/Field/Select/Chip/Card/Avatar/…), permission-aware **hooks** + api client, and the semver **`UI_API_VERSION`** gate. The host loader (`web/src/lib/plugin-loader.ts`, driven by `PluginRemotes`) reads each ENABLED plugin's remote from `/capabilities` `remotes[]`, version-gates it, `import()`s + `activate()`s it (registering its slots), **quarantines** failures, and on disable calls `unregisterPlugin` so its UI unmounts live. Base views render `<Slot>` and know no plugin: `IssueProperties` hosts `issue.panel.section`, a splat route → `PluginPage` hosts `route.page`. Backend: `PluginUiManifest.remote` + `ui_api_version` on the manifest; `/capabilities` surfaces enabled remotes; bundles are served at `/plugins/<name>/` from a stable `plugin-assets/` dir (`_mount_plugin_assets` in `app.py`, `RADD_PLUGIN_ASSETS_DIR`); external plugins are discovered via the **`radd.plugins` entry point** (`pluginmgr/discovery.py`). Builtin remotes live in `web/remotes/*` (built by `web/scripts/build-all.mjs` into `plugin-assets/`): `participants` (issue.panel.section), `milestones` (route.page CRUD). The acceptance example `examples/acme-notes/` is an independent project (own pyproject entry point + own web build) proving a third-party plugin loads with zero core edits. Verified in headless Chromium by `web/scripts/render-proof.mjs`. Tests: `tests/test_frontend_federation.py`.

**Plugin-UI depth (spec 94 addendum):** the SDK slot vocabulary grew: `view.type` + `dashboard.widget` (keyed by the type key, backed by kernel `registries.view_types`/`widget_types` from `ViewTypeSpec`/`WidgetTypeSpec` on `RaddPlugin`, surfaced in `/capabilities`), `plugin.manager.section` + `profile.section`, and SLQ-field registration (`registries.slq_fields`, `SlqFieldSpec` → `items/slq/compiler.py` routes an unknown field to it). **Per-contribution toggles are two-scope + plugin-owned:** a contribution renders iff enabled in BOTH the GLOBAL scope (instance-wide, admin — stored per-plugin in `InstalledPlugin.config`; `GET /plugins/contribution-settings` any-user + `PUT /plugins/{id}/contribution-settings` admin) and the PER-USER scope (Profile; `users.preferences` JSONB + `GET/PUT /auth/me/preferences`). The kernel forces nothing — a plugin mounts `<GlobalContributionToggles>`/`<UserContributionToggles>` (On/Off switch) into the `plugin.manager.section`/`profile.section` slots (`toggleable:false` opts a control-surface contribution out). A disabled contribution leaves EVERY manifest-driven surface too: `useDisabledNavPaths`/`useDisabledMatches(slot)` drop its sidebar nav link, its view-type/widget-type dropdown option, and show a `MissingPluginType` "turned off" notice for an existing view/widget of a turned-off type. `PluginRead` gained `name` (the slot-registry tag). `docs/plugin-ui.md` is the full map.

**Plugin manager / lifecycle (spec 93 / A4):** the `pluginmgr` core plugin owns `installed_plugins` (id/version/state/config) + the state machine (`discovery.py` finds bootstrap plugins from `config.modules` + installable ones from `config.installable_plugins`; `service.py` = install/enable/disable/uninstall). **Three plugin classes** by the `RaddPlugin.core` flag: **core bootstrap** (`config.modules`, `core=True`) — the tracker's spine (events/projects/auth/items/workflow/… + kernel machinery), locked always-on; **optional bootstrap** (`config.modules`, `core=False`) — integrations/features on by default but **disableable** (ldap, sso, ai, mcp, docs, dashboards, slas, csat, approvals, participants, gitlab, forgejo, googlechat, alertmanager, mailintake, jiraimport); **installable** (`config.installable_plugins`, off by default, enable to turn on — e.g. milestones). `boot.resolve_boot_paths()` loads core always, optional unless a DISABLED row exists, installable when ENABLED. `disable`/`uninstall` are guarded by `_ensure_no_dependents` (can't disable a plugin another loaded plugin `depends_on` — e.g. mailintake while csat is on) and core-lock (409). `boot.py` resolves the ENABLED non-core set at `create_app` time (sync read → added to the load set); `runtime.py` hot-mounts/unmounts a plugin's routers in the running app (pops the SPA catch-all so new API routes precede it). `GET /plugins` + `POST /plugins/{id}/{install,enable,disable,uninstall}` (instance-admin). `migrations/env.py` scans `installable_plugins` too so autogenerate never drops an installed-but-disabled plugin's table. Tests: `tests/test_plugin_manager.py`. **Admin UI:** `Settings → Plugins` (`web/src/routes/settings/plugins.tsx`) — state badges, a lock on core plugins, Enable/Disable on non-core; toggling invalidates the capabilities manifest so the sidebar plugin-nav updates live.

**Entity auto-wiring (spec 93 / A3) + north-star:** `kernel/entities.py` turns a declarative `EntitySpec` (field DSL, or a `model=` escape hatch) into a first-class feature: it builds the SQLAlchemy model (imperative Table mapping) into `Base.metadata`, and auto-registers the `<key>.created/updated/deleted` event types (→ automations/webhooks/audit), the `<key>.create/update/delete` CRUD-resource RBAC atoms, and a generic permission-guarded CRUD router (`crud_router`, mounted by `app.py` from `registries.entity_routers`). `ensure_tables()` (called in the lifespan) creates entity tables idempotently. The loader auto-wires on `plugin.entities`. The **`milestones`** plugin (`radd/modules/milestones/` — one `EntitySpec` + a `NavItemSpec`, `core=False`) is the north-star: declaring it lights up automations/RBAC/nav/CRUD with zero edits elsewhere (`tests/test_north_star.py`). It's not in the always-on `config.modules` bootstrap — it's a non-core plugin installed (migration `a29615cf474d`) + runtime-enabled via the plugin manager (§10). `config.bootstrap_plugins` is the placeholder for that lifecycle set.

**RBAC registries plugin-contributable (spec 93 / A2):** permission atoms + CRUD resources are no longer a closed enum/tuple. A plugin declares `permissions=(PermissionSpec…)` / `crud_resources=(CrudResourceSpec…)` in its manifest (or calls `kernel.register_permission`/`register_crud_resource`); the merged-view accessors in `auth/types.py` (`all_permission_keys`, `permission_scope_of`, `permission_description_of`, `implied_map`) fold them in LIVE alongside the builtin `Permission` enum / `CRUD_RESOURCES`. The union engine (`authz.combine_permissions`, `effective_permissions`, admin = `all_permission_keys()`) now flows atoms as **strings** (StrEnum members already are strings — builtins byte-identical), so a plugin atom appears in `GET /permissions`, is held by admin, and is grantable in a role. `RoleCreate/Update/Read.permissions` + `MeRead.permissions` + `PermissionRead.key` are `list[str]`/`str`; `RoleCreate/Update` validate atoms against `all_permission_keys()`. In the default config the registry is empty, so every accessor equals the builtin set exactly. Tests: `tests/test_rbac_registry.py`.

**Chokepoint-2 inversion (spec 93):** the `capabilities` core plugin (`radd/modules/capabilities/` + `kernel/capabilities.py`) serves `GET /capabilities` — it evaluates every plugin's `CapabilitySpec` (static `enabled` or a `check()` returning `{enabled, **detail}`). Feature/connector plugins declare their own capability in their manifest (`capabilities=(CapabilitySpec(...),)`); the `capabilities` plugin owns the infra flags (workers/smtp/mfa). `projects`' `/instance/status`, `/instance`, `/instance/login-options` now read the registry (`kernel.capabilities.capability_map()`) instead of inlining `bool(settings.*)`; `connectors` is derived from every `category=='connector'` capability, so a new connector appears with zero edits. Parity pinned by `tests/test_capabilities.py`.

**Chokepoint-1 inversion (spec 93):** automation triggers are no longer a hardcoded catalog. Each producing module declares its triggerable events in its manifest (`event_types=(EventTypeSpec(...),)` — the trigger metadata label/group/item_scoped/has_changes now lives next to the producer, not in a central list). The loader aggregates them into `kernel.registries.event_types`; `automations/catalog.py`'s `TRIGGERS` reads `registries.triggers()` live (PEP 562 `__getattr__`), so a new plugin's events appear as triggers with zero edits to automations. Parity is pinned by `tests/test_trigger_registry.py` (65-trigger snapshot).

Two app-level pieces outside the module system: `radd/middleware.py` (`CommitBeforeSendMiddleware` — buffers each HTTP response until the request's session has committed, closing the response-before-commit race FastAPI's yield-dependency teardown ordering creates) and SPA serving (`_mount_spa` in `app.py` — serves `web/dist` with SPA fallback when present, `RADD_WEB_DIST` overrides). One shared core util: `radd/smtp.py` (spec 62) — THE synchronous outbound-email helper (`send_message(to, subject, body, *, to_name, headers)`) over the `smtp_*` settings; callers wrap it in `asyncio.to_thread` and keep the empty-`smtp_host`-means-disabled guard themselves. Consumers: notify digests, mailintake acks + comment replies (spec 62), csat surveys (spec 65); the automation send_email action (spec 66) later. A second core util, `radd/worker.py` (`PeriodicLoop`) — THE background-loop scaffold (tick / log-don't-crash / sleep, restart-safe stop) every dispatcher-style module instantiates with its `run_once`, gate lambda (usually `run_workers`), and poll-interval lambda; used by webhooks, automations, search, notify (×2), csat, mailintake (×2), googlechat, and the SLA engine.

**Module-internal package splits (the barrel is the boundary).** When a module's `service.py` outgrows the 300-line rule it becomes a `service/` PACKAGE of per-concern modules stacked bottom-up with no cycles, and the package `__init__` is a barrel that re-exports **only the module's public surface** — never the `_`-prefixed helpers, whose privacy is the whole point of rule 1. `items/service/` is the reference: `visibility`/`queries` (leaves) → `relations`/`read`/`listing` → `links` → `core`, barrel = the same 25 functions the former god-file exposed. An intra-module caller that genuinely needs a helper imports the concern module directly (`from .service.visibility import _internal_visible` in `items/bulk.py`); a caller in ANOTHER module does not get one — it asks for a public function.

**Timesheet: group by epic.** The timesheet's grouping axis gained `epic` alongside issue/person/category. Each entry now carries its `epic` (the epic the logged item belongs to), hydrated in `timesheet.build` through a NEW public items seam — `items.service.epics_for_items(session, ids) -> {item_id: EpicRef}` — so the timesheet groups by epic without learning the hierarchy: one aliased child/parent/grandparent chain resolves the whole batch in a single query (the kind ladder caps depth at 3), the same shape `slq/ancestors.py` uses for `epic.*` but as a batch seam rather than a correlated subquery. An item that IS an epic maps to itself (time logged straight onto an epic belongs under it) — **since both sides share ONE definition, `items/hierarchy.py::nearest_epic_case`** (see the `epic` note below). "No epic" is a first-class row, not an error state: general worklogs have no issue at all and plenty of issues sit outside an epic, so folding them together would hide how much time never rolls up.

**`epic` is reflexive — an epic belongs to itself (spec 83 amendment).** `epic` names a CONTAINER, not a relative position: `epic = TD-3` returns TD-3 **plus** its issues and subtasks, and `epic.state != Done` returns each unfinished epic alongside the work it governs. Before this, `epic` was a strict ancestor, so an epic's epic id was NULL and it matched NO `epic.*` condition — not even negated ones, because `NOT (NULL IN (…))` is NULL — while spec 98's timesheet grouping already mapped an epic to itself. Two definitions of one concept; now there is **one**, `items/hierarchy.py::nearest_epic_case(item, parent, grandparent)` (self arm, then parent, then grandparent), which both consumers build and bind differently — `service/queries.py` joins it for a batch, `slq/ancestors.py` correlates it per outer row (correlating on the ITEM and outer-joining upward, since a parentless epic yields no row when you correlate on its parent). `parent`/`parent.*` are untouched: an item is never its own parent. **Behaviour change:** `epic IS EMPTY` / `epic = none` no longer match epics — they mean "work no epic governs", the exact complement of `IS NOT EMPTY`; `kind = epic` asks the old question. Epic nesting can't complicate the rule — `REQUIRED_PARENT_KIND` gives epics no parent kind, so every item has at most one epic in scope. `docs/specs/83-*.md` (amendment).

**Worklog SLQ — the timesheet's dialect (spec 98).** SLQ is now TWO dialects sharing one language. The worklog dialect is rooted at the WORKLOG because that is what the timesheet returns; an item-rooted query can never surface general worklogs (spec 59), which have no item to return, so this is a correctness requirement rather than a convenience. Fields are bare (the root is implied, exactly as item queries say `priority` not `item_priority`): `author`, `category`, `project`, `worked_on`, `time` (duration literals in the log-work language, resolved with the instance's hours-per-day), `note`, and `issue`. **`issue` carries the design's whole idea** — `issue IS EMPTY` (general time), `issue = DEV-123`, and `issue.<anything>` DELEGATED to the item compiler and wrapped as `worklog.item_id IN (SELECT id FROM work_items WHERE …)`. The delegation means this module never restates the item field surface: builtins, custom fields (`issue.cf.foo`), ancestors, labels and plugin fields all work here permanently, with nothing to keep in sync. It is exact, not an approximation — a worklog has exactly one issue, so per-condition delegation and a subquery select the same rows, which is why the braces/sub-query grammar was dropped. Autocomplete delegates the same way (`issue.assi` → the item dialect's fields, `issue.assignee = ` → its values incl. `me`/`none`) by splicing the prefix out and shifting the offset back. Reuses items' lexer/parser/helpers (generic query machinery, now exported from `items.slq`); supplies only a seven-field catalog + compiler + suggest. API: `GET /timesheet?q=` (compiled and ANDed onto the scope filters inside `timesheet.build(where=…)`, so a query can only NARROW what the actor may already see), `GET /timesheet/slq/validate`, `GET /timesheet/slq/suggest`. SPA: the shared `SlqFilterBar` gained a `dialect` prop; the timesheet passes `ApiPath.timesheet` and persists `q` in the URL. Solves the author≠assignee case that motivated it: `author = me AND issue.assignee != me`. `docs/specs/98-*.md`, `tests/test_worklog_slq.py`.

**Relational SLQ fields (spec 97).** SLQ can ask about what HAPPENED to an item, not only what it is: `logged_by` (timelogging) and `commented_by` (comments) find issues by who logged time on them / commented on them — `logged_by = me`, `commented_by = "alice@corp.example"`, `logged_by ~ alice`, with `!=` negated by the engine. No new machinery: both ride spec 94's `SlqFieldSpec` registry, so each module contributes a `Select` of matching work-item ids over its OWN table (plus the `auth.User` spine) and `items` never learns that worklogs or comments exist. One contract change — `item_ids` now takes `(contains, value, ctx: SlqFieldContext)`; the context carries `current_user_id` + an `is_me` flag, because `me` is a grammar sentinel that `helpers.plain()` rejects, so resolvers could not previously honour it. Itemless worklogs (spec 59) never match — no item to name. `commented_by` matches on authorship alone, so an internal comment can make its item match for someone who could not read it (existence, never content; the item still passes normal RBAC). `docs/specs/97-*.md`, `tests/test_relational_slq.py`.

**In-transaction hooks** (`radd/hooks.py`): a module can subscribe to another module's mutation and react *inside the same transaction* (`@hooks.on(ProjectEvent.PROJECT_CREATED)`). Use only when atomicity with the trigger is required (e.g. workflow seeds default states with the project); everything else belongs to outbox consumers, which run after commit.

## Connection rules

- Cross-module calls go through the other module's `service.py` public functions only. Models are private to their module (Alembic metadata aside) — **except the shared spine tables, below.**
- Every domain mutation calls `events.service.emit()` **in the same session/transaction** (the outbox guarantee). Event types are per-module `StrEnum`s (e.g. `ItemEvent.CREATED = "item.created"`).
- Custom fields must serialize **inline on the entity** in every representation (REST now; webhooks/MCP later). Never a side-channel endpoint. (See `research/architecture.md` — the Plane failure.)
- The `fields` registry is the single source of truth for dynamic schema. Consumers: item validation (now), OpenAPI (now, via marker scan), UI form config / MCP tools / webhook payload docs (later — same registry, no parallel definitions).
- **RBAC (spec 03, engine reworked by spec 06)** has one seam: routers (or the items/comments services, which resolve the project themselves) call `auth.authz.require(session, user, Permission.X, workspace_id=…|project=…)` → 403; `CurrentUser` → 401 when anonymous. Only `/auth/login`, `/auth/logout`, `/docs`, `/openapi.json` stay open. Roles are DATA: a user's effective permissions on a project are the **union** of their direct `project_members` role, their teams' `project_teams` roles, and — for members of the project's workspace — the builtin `viewer` floor (**open-visibility default**); instance admins and the workspace's admins hold every permission. Workspace-scoped checks: admin → all, member → floor. Unscoped checks (`/users`, `/workspaces` create, `/events`) use the caller's best membership anywhere. `require()` returns the effective-permission frozenset (callers reuse it — items derives `has_manage`/`comment.read_internal` from it without a second lookup). Never re-implement checks in modules — call the seam in `auth/authz.py`; new action classes = new `Permission` members + catalog entries in `auth/types.py`.

**Spine tables (the honest exception to the first rule).** ~130 cross-module model imports exist, and two tables are the de-facto shared spine the tracker joins against: `auth.models.User` (47 import sites across 25 other modules) and `projects.models.Project` (35 sites, 20 modules). Those two may be imported directly — user/project FKs and joins are how the tracker fits together. A few near-spine models (`fields.FieldDefinition`, `items.WorkItem`, `events.Event`, `workflow.State`) also cross module boundaries today; that's tolerated reality, not license — new cross-module needs still go through the owning module's `service.py`, emitted events, or a declared extension point.

## Frontend cache invalidation (the convention every module follows)

One domain object is cached under **many** TanStack Query keys (an item lives in
`["items"]`, `["viewItems"]`, `["slqItems"]`, `["item"]`, `["itemByKey"]`). If a
mutation forgets one — or a new module adds a new query that caches the same
entity — an edit made on one surface silently won't appear on the others until a
hard refresh. To make this **impossible to get wrong across modules**, invalidate
by ENTITY, never by key (`web/src/lib/cache.ts`):

- **Read queries self-declare what they cache:** every `useQuery`/`queryOptions`
  that returns a domain object sets `meta: entityMeta(Entity.item)` (list one tag
  per entity in its data — a query joining items+cycles tags both).
- **Mutations invalidate by entity:** `onSettled: () => invalidateEntities(queryClient, Entity.item)`
  — a predicate refreshes every query tagged with that entity, including ones
  added later by other modules. List every entity a mutation can change (e.g.
  commenting touches `Entity.comment` AND `Entity.item` for its `comment_count`).
- Optimistic writes still `setQueryData` the specific caches for an instant feel;
  the entity invalidation on settle is the safety net that keeps every surface live.
- **New module checklist:** add its object to the `Entity` map; tag its read
  queries with `entityMeta`; have its mutations call `invalidateEntities`. Then a
  future query anywhere that caches the same entity is refreshed automatically —
  neither side needs to know about the other. (Retrofitting the pre-existing
  non-item modules onto this is incremental; new modules start here.)

## Field grant semantics (spec 07)

A field's visibility is driven by its `field_permissions` rows (subject = a role id or team id, access = `read`|`write`), checked against the actor's `FieldAccessContext` (`role_ids` incl. builtin-derived + team-granted roles, `team_ids`, `has_manage`):

- **No rows for an access → that access is default-open**: read for anyone with `item.read`, write for anyone with `item.update`. (This is why converted defaults produce zero rows.)
- **Read rows exist** → the field's value is visible only if one of the actor's subjects holds a read OR write grant (writers may see what they write), or the actor has `project.manage`.
- **Write rows exist** → writable only via a matching WRITE grant (read grants never confer write) or `project.manage`. Corollary: a field with only read grants stays write-open to `item.update` holders.
- Grants are extra restrictions on top of action RBAC, never a bypass: without `item.read`/`item.update` on the project a grant is moot.
- Migration `fa2747459c4b` converted the old ladder: `min_read_role` admin → read grant for the builtin admin role, member → read grants for admin+member, viewer (default) → none; `min_write_role` admin → write grant for admin, member (default)/viewer → none; then dropped both columns.

## SLQ — the Radd Query language (spec 10)

`items/slq/` (`lexer.py` → `parser.py` AST → `compiler.py` SQLAlchemy; op tables in `catalog.py`). `GET /items?q=…` takes it; saved views store it (`views.query`). The grammar is FROZEN — frontends render their cheat sheet from it:

```
query     := [expr] [ORDER BY order (, order)*]
expr      := term ((AND|OR) term)*        # AND binds tighter than OR
term      := [NOT] (comparison | '(' expr ')')
comparison:= field op value | field [NOT] IN '(' value (',' value)* ')' | field IS [NOT] EMPTY
op        := = | != | ~ | > | < | >= | <=
value     := bareword | 'single' | "double" quoted | number | YYYY-MM-DD | today[±Nd|Nw] | me | none
order     := field [ASC|DESC]
```

Keywords case-insensitive; field names case-sensitive; quoted values are always literal (never sentinels/keywords). Builtin fields: `project` (key), `state` (name), `category`, `kind`, `priority`, `assignee` (email | `me` | `none`), `team` (name | `none`), `label` (`=` has, `!=` lacks, `IN` has any, `IS EMPTY` unlabeled), `title` (`~` case-insensitive contains / `=`), `key` (`= TD-12`), `parent` (key | `none`), `number`, `created`/`updated` (date comparisons with whole-day windows: `= d` means within the day, `> d` strictly after it), and the **planning fields (spec 14)**: `cycle` (`= name` \| `= none` \| `!=` \| `IS [NOT] EMPTY`; matches `cycle_id` by cycle NAME via subquery, workspace-unscoped like `state`), `release` (`= version` \| `= none` \| `!=` \| `IS [NOT] EMPTY`; by release VERSION), `blocks`/`blocked` (`IS [NOT] EMPTY` = has an outgoing/incoming `blocks` link — an EXISTS over `item_links`; `= <key>` = links to/blocked-by that item; `=` only, no `!=`/`IN`), `start`/`target` (plain Date-column comparisons — no whole-day windowing — `= != > < >= <=` + `IS [NOT] EMPTY`; **not sortable**), `flagged` (**spec 24** — first-class boolean: `= true` \| `= false`, sortable, autocompletes true/false, other values → 422), `starred` (**spec 24** — the requesting user's personal star: `= true` \| `= false`, an EXISTS over item_stars scoped to `current_user_id`), `rank` (**spec 24** — manual sort key, **`ORDER BY rank` only**: no compare ops, excluded from filter-field autocomplete) — plus **every custom field by bare registry key** (select/text/url: `= != ~ IN`; user: `= != IN`; multi_select: containment — `=` contains, `!=` lacks, `IN` contains any; number/duration/date: comparisons; boolean: `= true|false`; all cf support `IS [NOT] EMPTY`). Unknown field or type-invalid op → 422 `{detail, position}` (character offset), with a one-edit did-you-mean on unknown fields. Compilation is subquery-based (state/project/user/team lookups, EXISTS for labels, JSONB ops for cf — `@>` for equality, `->> ::cast` for ranges); labels resolve name→id through the labels service; cf typing uses the same key→definition map as the `cf` param (project registry when `project_id` is given, instance-wide otherwise). `ORDER BY` sortables: `created`, `updated`, `number`, `title`, `priority`/`kind` (enum rank), sortable cf types (cast per type); `created DESC` always appended as tiebreak/default. `!=`/`NOT IN` on relations follow SQL NULL semantics: items with the relation unset don't match (use `IS EMPTY`/`none` explicitly); scalar-cf `!=` means "has a different value"; multi_select/label `!=` means "lacks" (missing included). **Relative dates (spec 69):** every date position (`created`/`updated`/`start`/`target` + date custom fields) also accepts bare `today`, `today+3d`, `today-2w` (units `d`/`w`; a QUOTED 'today' stays literal, like the me/none sentinels), resolved at COMPILE time against the server date (`helpers.relative_date`, pure with injectable `today`) — a saved view using `today` shows results as-of query time; `today` leads the date-field suggest values (tier-sentinel, bare insert). **Ancestor fields (spec 83, `items/slq/ancestors.py`):** `epic` = the NEAREST EPIC ANCESTOR (an issue's parent, a subtask's grandparent — one aliased P/G self-join chain per condition deriving `CASE WHEN P.kind='epic' THEN P.id WHEN G.kind='epic' THEN G.id END` as a correlated scalar subquery; NULL for epics themselves and parentless items, so `epic IS EMPTY` covers both), `parent` stays the direct parent; the bare forms take `= key` / `!= key` / `IN (key, none)` / `IS [NOT] EMPTY` with keys resolved at COMPILE time through the spec-68 alias-aware `find_item_by_key` (a `compile_query` pre-pass like label resolution; unknown key → positioned 422 — a change from the old match-nothing `parent = key` subquery, so moved items keep matching under their pre-move keys). Sub-fields `epic.state`/`epic.category`/`epic.assignee`/`epic.priority` (+ the `parent.*` twins) mirror the item-level value semantics (state NAMES case-INsensitive here per the spec; category/priority enum-validated with positioned 422s; assignee `me`/`none`/email via the shared `builtins.user_match` helper) and compile to `<ancestor id> IN (SELECT id FROM work_items WHERE …)` — correlated comparisons, never joins — so OR/NOT and the SQL NULL rule hold (`!=`/`NOT IN` don't match items without the ancestor); cross-project ancestors (spec 80) match naturally since traversal is by id. Filter-only: none are sortable (`ORDER BY epic.state` → the standard not-sortable 422); suggest completes all nine field names and reuses the item-level value sources (state names, categories, users incl. `me`/`none`, priorities; bare `epic`/`parent` offer `none` + item keys).

## Known simplifications (fix when they matter)

- OpenAPI is rebuilt per request (no cache) and the field-schema cache refreshes in-transaction on field creation — a rolled-back field create could leave the cache one step ahead until next startup/mutation. Move refresh to an event consumer when the worker lands.
- Field schema in OpenAPI is instance-wide; per-project scoping is enforced at validation time but not yet reflected per-project in docs.
- RBAC coarse edges: workspace/project/team/label listings are visible to any workspace member anywhere (not filtered to their workspaces); `GET /events` is instance-wide for any workspace member (trusted consumers); `item.created`/`item.updated` event payloads and webhook deliveries carry FULL `custom_fields` regardless of field grants, and `comment.*` payloads carry the excerpt even for internal comments (trusted consumers); any workspace admin can create new workspaces (unscoped admin rule) and the creator is not auto-membered into a workspace they create (instance admins don't need it; others would lock themselves out — add self-membership when non-admin creation matters).
- Actor threading: every mutation emits with `actor_id` except default-state seeding, which runs via the in-txn `project.created` hook — the hook seam doesn't carry the actor yet, so those `state.created` events are actor-less (system-seeded).
- Auth gaps: expired sessions are never pruned (rows just stop resolving); no user update/deactivate endpoint; PAT `last_used_at` writes are throttled (`RADD_TOKEN_LAST_USED_THROTTLE_SECONDS`, default 60s) so it's approximate.
- Roles (spec 06): builtin permission SETS are immutable (409) but builtin name/description/position may be patched; nothing stops a workspace from removing/demoting its last admin (instance admins can always recover); custom roles may list workspace-scoped permissions (`role.manage` etc.) but project-scoped checks never consult them — the catalog's `scope` field is the UI's guard; `project_teams` POST still accepts the legacy `role` KEY (resolved against the workspace's roles) so pre-06 clients/importer keep working; role permission grows are visible immediately (no caching), every check re-queries.
- Field grants (spec 07): the ladder shim is deleted from authz; `teams/types.py` still defines the now-unreferenced `ProjectRole` enum (its docstring says spec 07 retires it — remove with the next teams change). Deleting a role/team leaves no dangling grants problem for roles (RESTRICT via project_members/project_teams guards deletion of referenced roles, and unreferenced-role grants just stop matching) but grant rows pointing at deleted subjects are not garbage-collected — they keep the field restricted, which fails closed. `FieldDefinitionCreate` no longer takes visibility args (grants are set post-create via PUT); old clients sending `min_read_role`/`min_write_role` get them silently ignored. `item.created`/`item.updated` payloads embed the acting user's `comment_count`.

- Automations (spec 15): the engine runs **in-process** like the webhooks dispatcher (single-instance assumption; multi-replica needs the worker entrypoint + `FOR UPDATE SKIP LOCKED`; pure polling, `RADD_AUTOMATION_POLL_INTERVAL`). The **loop guard is the actor marker**: engine-applied item events carry `actor_id = SYSTEM_ACTOR_ID` and are skipped — so a *human/API* action is never confused with an engine one, but two rules cannot deliberately chain (a rule's effect can't trigger another rule); depth-capped chaining is the upgrade if that's ever wanted. The system actor is a real `users` row (fixed id `00000000-…-000000a70a70`, instance-admin, null password so it can't log in) **seeded by this module's migration** — a data insert into another module's table, done in the migration rather than at runtime; it shows up in `GET /users` and as the actor on engine-made changes. `Permission.AUTOMATION_MANAGE` was added to `auth/types.py` (where the `Permission` enum + catalog live), not just `authz.py` as the spec's path hint said, so the catalog-totality test stays green; it's workspace-scoped, so workspace/instance admins hold it and plain members don't (widen the member floor when member-authored rules matter, same as `CYCLE_MANAGE`). `add_label`/`remove_label` read the item's current labels via `items.get_item` (labels replace wholesale on `ItemUpdate`, so there's no single-label add op); each action is a separate `update_item`, so a multi-action rule emits several `item.updated` events (all self-skipped). A stored condition/action that later references a deleted state/field just stops matching or skips+logs at apply time (validated only on write).
- Frontend (Phase 2): board/list fetch one page of items at the API cap (200) — no pagination UI yet; list filters and the board kind filter run client-side over that page (switch to the server-side `kind`/`assignee_id`/`team_id` query params when pagination lands); item routes resolve `$number` → id by scanning the fetched list; parent is set at creation only (no reparent control in the detail panel); `user`-type custom fields render as a plain id text input; comment edit/delete not exposed.
- Frontend (Phase 3): the single-workspace assumption (`workspaces[0]`) applies to every settings page, which matters on instances with multiple (demo) workspaces; teams' project-attachment list fans out one `GET /projects/{id}/teams` per project; field-definition rows show `viewer`/`member` fallbacks while the API omits `min_read_role`/`min_write_role` (values ARE sent on create); labels can't be renamed/deleted (no endpoints).
- Frontend (spec 09 Phase A): view boards are read-only (no cross-column DnD — moving a card along an arbitrary group axis isn't wired); the New-view affordance is gated on `view.manage`, so pure viewers can only create their (server-allowed) personal views via the API; workspace-spanning views group `state` buckets by state NAME across projects; view item fetches are one page at the 200 cap (same pagination gap as the board); `shared`/`project_id` are create-only server-side, so the Edit dialog doesn't offer them; settings pages map creates to backend rules (fields/labels → workspace-scope `project.manage`, states → that project's `project.manage`, teams → `team.manage`, roles → `role.manage`, members → `workspace.manage`).
- Frontend (spec 11): SLQ probes fetch one page at the 200 cap, so the live match count tops out at "200+"; the probe (and ad-hoc list results) skip fetching entirely on an empty draft; `swimlane_by` is only pickable once Columns is set (no swimlanes over the implicit state fallback of an ungrouped board); collapsed-lane state is per-browser localStorage (not synced); `cf.<key>` lane/column buckets come from the registry field's option list in registry order, plus any stale values still on items, plus the trailing None bucket — multi_select fields are not axis options (backend restricts axes to select); the list route's dropdown filters still apply client-side ON TOP of an active SLQ result.
- Frontend (spec 19): the roadmap needs BOTH `start_date` and `target_date` to place a bar (single-date items go to the Unscheduled tray); drag-to-reschedule is not wired (dates are edited on the item detail's planning row); `blocks` dependencies render as a marker chip (⛔ blocking key) rather than drawn connector lines; the time axis is fixed-scale (`ROADMAP_DAY_WIDTH`), no zoom, and inherits the board's per-project 200-item page cap; velocity lists only FINISHED cycles (status derived server-side vs today) and burnup `completed` counts only items that entered a done state WHILE assigned to the cycle (assign-then-complete order matters — re-assigning already-done items grows scope but not completed); throughput/CFD default to the last 56 days at week interval; SVG charts scale a fixed 640-unit viewBox to card width with only native `<title>` hover (no rich tooltips/crosshair).
- Frontend (spec 18): the cycle items page fans out one `GET /items?project_id=` per project and client-filters by `item.cycle?.id` (no server cycle filter), inheriting the board's 200-item-per-project page cap; native `<option>`s can't carry per-option colour, so the cycle/release selects show a status dot only for the *selected* value; cycle status is derived server-side against the server's "today"; cycles list workspace-wide in the sidebar in API order (no active-first sort or collapse); the cycle page groups by state *category* (universal across projects) rather than per-project state names; deleting a cycle/release an item still references is left to the backend (the UI doesn't pre-warn), and the add-link input's TYPED form takes a bare number or same-project key (`target_number` addressing) — cross-project targets (spec 80) come from the typeahead, which submits by id.
- Frontend (spec 20): the rule-condition probe passes `workspace_id` to `GET /items` which the endpoint has no scope param for and silently ignores, so the live "N items match" count spans every readable item rather than strictly the workspace (validation/parse-error behaviour is unaffected); the "Test on an item" panel only appears once the rule is persisted (the `/test` dry-run needs a saved rule id, so the flow is Save → Test); `set_state`/`set_release` action params are free-text name/version inputs with datalist suggestions fanned out across the workspace's projects (a workspace-wide rule resolves the name per the item's project at apply time, and the engine skips unknown names) — those suggestion lists inherit the board's 200-item-per-project cap; discovering forms/rules in-app (the settings lists + the sidebar New-from-form links) requires `form.manage`/`automation.manage`, so a pure `item.create` submitter can open a form's submit page by URL but can't browse to it; work items have no DELETE endpoint, so items created by form-submit verification persist (test residue).
- Time logging (spec 22): **`Permission.TIMESHEET_VIEW` is workspace-scoped → held by workspace/instance admins only** (custom roles can't hold workspace-scoped permissions in the current model, same shape as `CYCLE_MANAGE`); "roles that grant it" is the admin role, and everyone can always see their OWN timesheet (a caller without it is forced to `user_ids={self}`). `Permission.WORKLOG_WRITE` WAS added to the builtin **member** role (members log their own time) — `test_authz.py`'s exact member set was updated to match, and migration `b154d8429f77` backfills it into existing builtin admin/member role rows. The timesheet is **unpaginated + recomputed per request** and includes worklogs from projects later disabled (data isn't deleted); it reads `items`/`workspace` models directly in one join (tolerated inward read, like reporting reads `events`). Estimate is a single **original estimate**; remaining = estimate−logged (no separately-adjustable remaining). `worklogs.worked_on` is a plain Date (no time-of-day). Work categories have no hard DELETE (archive only; `category_id` is SET NULL as a backstop). Editing/deleting a worklog doesn't require the project still be enabled (cleanup after disabling stays possible); only creating worklogs/estimates does. The frontend timesheet person filter is single-select (the endpoint accepts multiple `user_id`). Existing workspaces' stored builtin role rows aren't otherwise reconciled (admins hold everything regardless), mirroring the `form.manage` note.
- Cycle view axis + staging cycles (spec 23): the `cycle` **header set is resolved client-side** from `cyclesQuery` (workspace cycles) — `GET /items` still has no cycle scope param, so a cycle-grouped view inherits the board's 200-item page cap and buckets what it fetched; items whose cycle is filtered out by `cycle_filter` (or references a cycle absent from the list) are **dropped from display**, so the group counts can sum to fewer than the SLQ total (only when a filter hides cycles). `cycle_filter` is a display regex (compile-validated server-side since spec 56) but still not applied as an SLQ item filter (empty staging cycles have no items to match). `ViewBoard` **columns are not collapsible** (only `ViewList` sections are), and `ViewSwimlanes` lane headers don't render the cycle `detail`/progress (only name+count) — the summary shows for `group_by=cycle` list sections / board columns. Completed cycles still show by default (ordered last, collapsible — no auto-hide). A cycle with exactly one date is accepted by the backend (→ DRAFT) though the settings modal steers to both-or-neither; `active_cycles`/velocity are unaffected (NULL dates never match the active predicate / the COMPLETED filter), and `burnup` **409s** on a draft cycle. Draft `CycleStatus` is derived (undated), so a *scheduled* cycle you don't want active yet can't be forced to draft without clearing its dates.
- View interaction (spec 24): cross-bucket drag / context menu / bulk / rank / star all live on **saved views** (the ad-hoc project list & board routes are unchanged). Bulk actions fan out N PATCHes (N settle-invalidations) — fine at studio scale; a `POST /items/bulk` is a later optimization. `kind` isn't draggable (create-only) and workspace-spanning `state` buckets are name-keyed so state DnD needs project scope. Manual **rank is a single global order** over all items (not per-view/per-bucket) — within any bucket items sort by that shared rank; within-section drag-to-reorder is **list-view only and enabled whenever the list is rank-ordered** (the default when a view has no explicit non-rank `ORDER BY`; board/swimlane reorder deferred; boards keep rank on cross-bucket moves so items land at their rank position). The default `GET /items` order is now `rank ASC` (was `created DESC`) — rank is backfilled/assigned newest-first so lists look the same but are draggable; a view sorted by an explicit field (`ORDER BY priority`) disables reorder. Rank reorder holds no lock (last write wins) and the rebalance respaces ALL items in one pass (fine at studio scale). Personal **star** is per-user; because hydration is shared, the acting user's `starred` (like `comment_count`) rides along in `item.updated`/`item.created` event payloads — harmless for the trusted stream, not a cross-user leak in the API (reads are per-actor). `flagged`/`starred`/`rank` are the first builtin boolean/EXISTS/sort-only SLQ fields; `rank` is excluded from filter-field autocomplete (sort-only).
- Reporting (spec 16): every report **recomputes from the event log on each request** — no projection/materialized table (acceptable at prototype scale; fold `item_state_timeline` into a read model when report latency bites). It reads the `events` table directly (`events.models.Event` + items' `ItemEvent`/`ItemEntity` event-type enums) because the outbox has no query-by-entity service seam yet — a tolerated inward read of a dependency, like the events↔auth edge. Transition times come from `Event.created_at`, so history is anchored to when events actually fired: a report window only sees events that occurred inside it (a demo that mutates "now" surfaces its data at "now", not in a backdated cycle window — so burnup/velocity demos use an active/completed cycle whose window brackets today). Time-in-state counts only *completed* stays (open final segments excluded), so a category every item is still sitting in reports no row; velocity/burnup treat an item as the cycle's if it was assigned at the moment it entered done (multiple done re-entries are deduped per item for velocity).
