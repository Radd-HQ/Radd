**Findings, in priority order.** P1 means fix before shipping; P2 means a concrete correctness or usability regression that should be addressed. Reproduced findings had probes in `probes.py` (removed; see above). Static findings are explicitly distinguished.

1. **[P1] Auto-watch can restart the same automation indefinitely, bypassing both self-suppression and the depth cap.** RADD-1320 interacts badly with RADD-1308/1315. The new [watch-event emission](../../server/src/radd/modules/notify/service.py#L54) runs later in the notification consumer. Its [caller](../../server/src/radd/modules/notify/consumer.py#L491) does not restore the original event's automation cause. The resulting `item.watched` event has `automated=false`, no rule ID and depth zero. A rule `item.watched → create issue` creates an issue, notification processing auto-watches its reporter, and the same rule runs again. Every new issue is depth 1, so the three-level cap never helps. This can create an unbounded stream of issues, events and notifications without opting into chaining. **Reproduced:** the probe continues beyond the configured cap and checks every reset. **Improve:** propagate causation through derived events in workers, including the originating rule ID/depth. Preserve silence during historical bootstrap, too. Add a test that drains both automation and notification consumers together; the existing chaining tests drain only automations.

2. **[P1] Validation's “draft-only” template restriction can disclose another issue's data to a submitter.** RADD-1329 allows `{{item.*}}` in [verdict messages](../../server/src/radd/modules/automations/verdicts.py#L78) on the premise that it describes the draft. But [rendering](../../server/src/radd/modules/automations/executor.py#L660) reads the current packet's item, which a search source can replace. A valid graph `validate → find an issue in a private project → warn("{{item.title}}")` returns that private title as submission feedback. **Reproduced:** the real intake service returned “Draft: Confidential acquisition” to a member whose direct read of that private issue was denied. The administrator-created graph passed normal save validation. The graph must be configured by an automation administrator; the exposure is to whoever later submits, including a public-form user. **Improve:** retain an immutable original draft reference and use a dedicated restricted renderer for all submitter-facing messages. Validate data provenance rather than just token spelling. Also review relayed findings and hidden fields against that boundary.

3. **[P1, upgrade/product regression] Several existing workflows stop after upgrading, and some configuration is destroyed.** This is intentional in the implementation, but a bad upgrade policy. Mail receipts and resolution messages are removed; [the migration deletes customized mail settings](../../server/migrations/versions/d1318mailorigin_comment_origin.py#L44). Existing VCS time mirrors are [all set to off](../../server/migrations/versions/d1321mirror_repo_mirror_time.py#L25). VCS merge transitions and release sweeps, Alertmanager comments/labels/resolve transitions, and the Google Chat consumer are also removed without equivalent enabled rules being migrated. The settings page's pointer to templates does not restore any of this. There are no supplied VCS automation templates in this range. **Impact:** customers receive no acknowledgement or completion email, merged work stops advancing, releases stop sweeping, time records become stale, and chat/alert updates disappear while the application still looks healthy. **Evidence:** migrations, removed callers and template definitions; not an upgrade of a production database. **Improve:** convert existing enabled behavior and custom text into visible, enabled, scoped automations. Preserve repositories already mirroring. Use disabled templates/off defaults for newly configured behavior. Where conversion is ambiguous, retain compatibility until an administrator reviews the replacement. Publish a concrete migration summary, including what was retained, converted or needs attention.

4. **[P1] Alertmanager receiver/project boundaries do not scope deduplication.** The new receivers select a project, but [the lookup](../../server/src/radd/modules/alertmanager/service.py#L64) and [database mapping](../../server/src/radd/modules/alertmanager/models.py#L35) still use fingerprint alone, instance-wide. Receiver B can emit repeat/resolution events targeting an issue created by receiver A in another project. The event says B received it, but its item is A's. **Reproduced:** identical alerts delivered to two receivers mapped to different projects create only the first project's issue. **Impact:** the second project's alert disappears, and enabled resolve automations can act on the wrong project's issue. A fingerprint identifies alert labels, not a globally unique monitoring installation. **Improve:** use `(receiver_id, fingerprint)`, or an explicit shared alert-source identity when multiple receivers intentionally share deduplication. Migrate legacy mappings to the seeded receiver. Test firing and resolution across two projects.

5. **[P1] Contributed-node rendering drops unresolved-variable errors; publishing can create a literal `{{…}}` version.** The new [context renderer](../../server/src/radd/modules/automations/executor.py#L667) discards `Renderer.misses` and the rendering trace. Built-in actions use those misses to skip when an upstream named producer supplied nothing. The [publish node](../../server/src/radd/modules/releases/automation.py#L87) instead accepts any nonempty rendered override. **Reproduced:** a valid saved manual graph ran its classifier’s `unavailable` branch and stored a release whose version was literally `{{classify.answer}}`. The classifier response was stubbed; graph saving, execution, rendering and release persistence were real. On a project with release transitions, that action also invokes the sweep against that version. Page comments can similarly publish raw placeholders. An upstream unavailable/fallback branch is a realistic source of missing outputs even when the graph was valid when saved. **Improve:** give contributed nodes the same structured render result as built-ins, with missing-variable refusal enforced centrally before apply and recorded in run history. Keep optional payload-token handling separate from missing named outputs. Test an upstream producer failure followed by a publish action.

6. **[P2] The verdict migration promotes shared advisory paths to required paths.** [Migration reachability](../../server/migrations/versions/d1329verdict_validation_verdict_nodes.py#L90) unions all required triggers' reachable nodes. A check shared by one advisory trigger and one required trigger becomes a single Block node. Both triggers then reach it and both get required bindings. A form/project that previously allowed submission after advice can start refusing it after upgrade. **Reproduced:** two trigger modes sharing `validation.fail` migrate to `{'advisory': True, 'required': True}`. **Improve:** preserve each entry point's semantics by cloning divergent branches or maintaining trigger-specific verdict policy during conversion. Test shared subgraphs, not only one-trigger graphs. Retain the original version data so migration parity can be audited.

7. **[P2] The supplied resolution-email template ignores automated resolutions.** Its trigger (`mailintake/templates.py:54`, since deleted) does not set `include_automated`. Consequently an Alertmanager resolve automation or the new release-publish/sweep action can close an issue without triggering the supposedly equivalent completion notice. Manual closures work, which makes this particularly confusing. The retired mail consumer did not apply the automation loop guard. **Reproduced:** the enabled template binds to ordinary `item.updated` events and is absent from automated bindings. **Improve:** explicitly include other automations' changes for lifecycle-notification templates and show that policy in their description. Test the complete alert-resolved → transition → customer-email chain. If the global depth budget intentionally stops delivery, surface the suppression reason instead of leaving it invisible.

8. **[P2] The replacement resolution flow loses previous recipient and duplicate-suppression behavior.** This is separate from whether the template runs at all. The new graph checks “state changed” and “current category is done,” so Done → another Done-category state sends another completion notice. It has no CSAT exclusion, even though the survey also announces resolution. Finally, `to: contact` uses the singular recipient resolver (`automations/email_action.py:156`, since deleted), whereas the deleted planner used the plural external-contact recipient list. **Impact:** duplicate notices for some customers and no completion notice for additional contacts on the same thread. **Evidence:** comparison with `v0.48.0:server/src/radd/modules/mailintake/resolved.py` and `reply.recipients_for`; no SMTP delivery was performed. **Improve:** provide reusable “entered category” conditions and recipient-set resolution, and retain the CSAT coordination in a dedicated desk-notification action or policy. A template can orchestrate those domain rules without reimplementing them incompletely.

9. **[P2] “State category is” is advertised as event-independent but still reads only the event.** [The new spec](../../server/src/radd/modules/automations/builtin_routers.py#L101) sets `reads_event=False`. Its evaluator still reads `facts.payload.item.state.category`. Manual item seeds, validation facts and scheduled searches do not populate that field, so newly accepted graphs take the false branch regardless of the seeded issue's actual state. **Reproduced:** a saved manual graph testing the seed's actual category evaluates false. The evaluator pre-existed; the regression is the new classification allowing eventless graphs to use it as an item-state check. **Improve:** split event-snapshot conditions from current-subject conditions. Implement the latter against packet subjects with explicit per-item/set semantics, or mark this node event-dependent until that exists.

10. **[P2] Deleting the last environment-seeded Alertmanager receiver does not stay deleted.** [Startup seeding](../../server/src/radd/modules/alertmanager/service.py#L195) claims a deleted row never returns, but checks only whether the table is empty. With the original environment token still configured, deleting the final receiver and restarting recreates an active receiver. **Impact:** a deliberately removed integration becomes active again. **Reproduced:** called the actual startup seeding function, deleted the last receiver, then called startup seeding again with the same environment token. An active receiver with a new ID appeared. The test substituted flush for commit to retain transaction rollback; it did not restart a deployed server. **Improve:** record a durable seed-completed marker, independent of whether rows exist. Distinguish temporary deactivation, deletion and explicit reseeding in the UI. Test delete → restart with seed variables still present.

11. **[P2] Plugin search can report no results even when matching readable entities exist.** [Generated search](../../server/src/radd/kernel/entities.py#L210) limits the global alphabetical candidate set before applying permissions. At `limit=5`, 25 earlier matches in inaccessible projects hide every later accessible match. **Impact:** Cmd-K and `#` mentions appear broken for ordinary members while working for administrators; increasing unrelated private data can make a previously findable entity disappear. **Reproduced:** with real database rows and role grants, a member found a readable milestone by its specific title, but a broader search returned no results when 25 private matches sorted first. **Improve:** apply readable-project filtering before limiting and implement relation filters in SQL where available. For remaining per-row checks, scan stable chunks until enough readable results are found or report explicit truncation. Keep the new fail-closed row-access fix.

The product should keep common setup close to the integration that needs it: Email should show acknowledgement/completion policies and whether they are active; VCS should show merge/release policies; Alertmanager should show resolve behavior. Those controls can create and link to ordinary automations underneath. Requiring every administrator to assemble a graph to recover basic integration behavior adds setup cost without making the engine more extensible.

The first fixes should establish shared invariants: (1) causation survives workers; (2) submitter-facing feedback can only read approved draft data; (3) renderer failures prevent mutation; (4) receivers isolate their subjects; (5) upgrades preserve enabled behavior. Then restore mail parity and validation migration semantics, and address the smaller search/editor issues. Broadly reverting the registry work would discard useful improvements without addressing those contracts.
