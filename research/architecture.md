# Architecture research: metadata-driven schema, plugins, events, AI-native design

Research date:

## 1. Metadata-driven schema

**How the reference systems do it.** Three distinct camps:

- **Real DDL driven by metadata (Directus, Baserow, Strapi).** Directus keeps a "dual schema": actual database tables/columns plus system tables (`directus_collections`, `directus_fields`) holding rendering/validation/permission metadata; field creation runs real `ALTER TABLE` via its FieldsService with DDL + metadata writes wrapped in one transaction, and the REST/GraphQL API is generated at runtime by introspecting the DB and merging metadata (https://directus.com/docs/getting-started/data-model). Baserow (Django) creates a real Postgres column `field_{id}` per user field. Strapi is the weakest fit: content-types are `schema.json` files synced to tables at startup — developer-time, not runtime, schema change; renaming a field drops and recreates the column, orphaning data.
- **Metadata layer over external DBs (NocoDB).** Logical model in a metadata store, physical schema in the user's DB, services keeping the two + caches in sync. Powerful but the sync machinery is the most complex and bug-prone part of the codebase.
- **Pure metadata objects (Attio, Plane).** Attio's model is objects → attributes → records → lists, with attributes creatable over the API and the whole product (UI, API, automations) reading the same attribute registry (https://docs.attio.com/docs/objects-and-lists). Plane added Work Item Types + custom properties as separate property-definition/value tables with dedicated endpoints — and hit the classic bolt-on failure: custom properties don't appear in the main work-items API response (https://github.com/makeplane/plane/issues/8654). That bug is exactly what our requirement must prevent: fields must live in the entity's primary serialization path, not a side-channel API.

**Storage: JSONB vs EAV vs runtime DDL.** 2026 consensus is firmly JSONB-first for dynamic attributes on Postgres. EAV loses on every axis (each filter becomes another self-join, writes touch many rows, everything stored as text). Runtime DDL gives real types and per-column indexes but couples every field edit to a migration engine and complicates ops; justified when the product *is* a database builder, less so for an issue tracker with a strong fixed core. JSONB caveats: no DB-level FK/type enforcement (validation moves to app layer), hot-row contention on wide documents.

**Indexing JSONB.** GIN `jsonb_path_ops` = 3–4x smaller index and faster `@>` containment than default `jsonb_ops`, but only supports containment operators. GIN maintenance can cut insert throughput 30–50% on write-heavy tables — if only a few custom fields are filtered on, expression indexes on those keys (created on demand, driven by the field registry marking a field "indexed") are dramatically cheaper.

**Keeping OpenAPI in sync.** Directus is the model: OAS generated live from current collections/fields at `/server/specs/oas`, so it can never drift. General principle: one canonical metadata registry; all representations (REST serializers, OpenAPI, GraphQL, UI form config, MCP tool schemas) generated from it on demand — never maintained separately.

**Recommendation.** Hybrid: fixed relational columns for core issue fields (status, assignee, project — keep FKs and workflow logic honest) + one `custom_fields JSONB` per entity + a `field_definitions` table (name, type, JSON Schema validation rules, options, indexed?, AI-visible?, per-project scoping). Validate writes against the registry with JSON Schema; emit typed OpenAPI component schemas from the same registry at a live endpoint; create expression/GIN indexes lazily when a field is flagged indexed. This is the Attio model with Directus's live-OAS trick. Pitfall to design around from day one: Plane's mistake — custom fields must serialize inline on the entity everywhere (REST, webhook payloads, MCP), not behind separate endpoints.

## 2. Plugin architecture

- **In-process (Redmine/Rails engines):** plugins monkey-patch core classes; every upgrade breaks them; zero isolation. Avoid as the third-party surface.
- **Sidecar/RPC subprocess (HashiCorp go-plugin):** Mattermost and Grafana build on this; crash isolation yes, language freedom only with gRPC variant, no security sandbox, operationally simple.
- **Out-of-process, API+webhooks only (GitLab):** no server plugin system by design; total language freedom, perfect isolation; costs latency, no UI extension points, every integration is its own deployable — a real burden for casual authors unless you ship a runner.
- **Sandboxed FaaS (Atlassian Forge):** zero-trust hosted apps; right for a SaaS marketplace, heavy to replicate self-hosted.
- **Sandboxed WASM (Extism, Shopify Functions):** production-grade for server-side by 2026 (WASI 0.2, Component Model), BUT **Python as a guest language is still poor** — componentize-py can't run C-extension libraries; practical Python-in-Wasm is MicroPython, a tiny subset. Pipeline TDs live on `requests`, ftrack/ShotGrid API clients, and studio site-packages — none run in Wasm.
- **The decisive precedent for VFX:** ShotGrid's `shotgunEvents` — a Python daemon that tails the event stream and dispatches to plugin files exposing `registerCallbacks()`, with hot reload (https://github.com/shotgunsoftware/shotgunEvents). Every studio pipeline TD already knows this pattern; ftrack's event listeners are the same shape.

**Recommendation.** Primary surface = out-of-process: the event stream + REST API, plus a first-party **Python connector SDK and runner** cloning shotgunEvents ergonomics (drop a `.py` file with `register(events)` into a directory; runner handles subscription, offsets, retries, hot reload, per-connector process isolation and supervision). Full CPython, full studio site-packages, crashes isolated, versioned against a stable API rather than internals. Skip in-process plugins entirely; keep Extism/Wasm as a later option for untrusted marketplace plugins.

## 3. Events and webhooks

- **Producing events:** transactional outbox — domain change + event row committed in one ACID transaction. At modest scale a poller over the outbox table is fine; the outbox schema doesn't change if you later switch poller→CDC (Debezium hazard: unbounded WAL growth when connector lags — cap with `max_slot_wal_keep_size`).
- **Bus sizing:** Postgres LISTEN/NOTIFY is at-most-once, non-persistent, ~1k msg/s ceiling, 8KB payloads — use only as a *wakeup signal*, never as delivery. Kafka unambiguously overkill. For a single-Postgres self-hosted product the right-sized answer is **no broker at all**: an append-only, monotonically-ordered event table (the outbox, retained) with per-consumer offsets, LISTEN/NOTIFY for low latency, polling fallback. Plugins, webhook dispatcher, search/embedding indexer, and AI agents are all just named consumers with their own cursors — one uniform stream, replayable from any offset.
- **Webhook delivery:** adopt the Standard Webhooks spec (Svix-led; adopted by OpenAI, Anthropic, Supabase, Twilio): HMAC-SHA256 over `id.timestamp.payload` with `webhook-id`/`webhook-timestamp`/`webhook-signature` headers (https://www.standardwebhooks.com/). Delivery per Svix's model: 2xx within ~15s = success, exponential backoff with jitter (immediate, 5s, 5m, 30m, 2h, 5h, 10h, 10h), dead-letter with manual replay, auto-disable endpoints failing for days. The MIT-licensed Svix server is embeddable if desired, but at this scale a dispatcher consuming the event stream into a Postgres-backed job queue is a week of work and one less service.

## 4. AI-native design

- **MCP built in.** Current spec 2025-11-25 (Streamable HTTP transport, OIDC discovery) RC in flight. Ship an MCP server *inside* the product on Streamable HTTP, sharing the REST layer's auth and generating tool input schemas from the same field-definition registry, so a new custom field appears in `tools/list` immediately. MCP supports `notifications/tools/list_changed` but client support is patchy — keep the *tool list* stable (create_issue, update_issue, search_issues, get_schema, run_saved_view…) and put the dynamism in each tool's JSON Schema `properties`, refreshed per session. Naive 1:1 OpenAPI→MCP conversion yields bloated tool sets; curate a small agent-shaped set generated directly from metadata.
- **Provider-agnostic LLM.** OpenAI-compatible chat-completions API is the 2026 lingua franca: vLLM and Ollama expose it natively; LiteLLM fronts 100+ providers (incl. Anthropic) behind one endpoint with routing/fallbacks/cost tracking. Product design: all internal AI features call one configurable "OpenAI-compatible base_url + model + key" (optional native Anthropic path); recommend LiteLLM proxy for multi-provider studios. Makes "self-hosted Llama on vLLM" and "Claude API" the same code path.
- **Semantic features.** pgvector 2026: parallel HNSW builds, `halfvec`, iterative scans for filtered queries. Hybrid retrieval — vector ANN + Postgres FTS fused with Reciprocal Rank Fusion — measurably beats pure vector (~62%→~84% precision in one benchmark). Linear's Similar Issues runs exactly this stack (pgvector cosine, embeddings partitioned by workspace, tens of millions of issues). Wiring: the embedding indexer and triage agent are ordinary consumers of the event stream — on `issue.created`, embed (title+description+custom fields), run similarity for dup candidates, one grounded LLM call for label/owner suggestions written back via the same MCP tools human agents use. AI agents are just MCP clients with scoped service accounts — that symmetry is what makes the system auditable.

## Synthesis

Build a Postgres-only modular monolith (Python — FastAPI/Pydantic) around a single **field-definition registry**: core issue columns stay relational, custom fields live in one JSONB column validated by registry-derived JSON Schema, with lazily-created expression/GIN (`jsonb_path_ops`) indexes; the registry generates the REST serializers, a live Directus-style `/openapi.json`, the UI form config, and the embedded MCP server's tool schemas, so a new field propagates everywhere with zero code. Extensibility is deliberately boring: a retained transactional-outbox event stream in Postgres (LISTEN/NOTIFY as wakeup, per-consumer offsets, replayable) feeds three uniform consumers — a Standard-Webhooks-compliant dispatcher with Svix's retry/DLQ discipline, an embeddings/triage worker on pgvector hybrid search with RRF, and a shotgunEvents-style Python connector runner (drop-in `.py` files, hot reload, per-connector process isolation) that is the ftrack/source-control integration surface pipeline TDs already know. No Kafka, no NATS, no in-process plugins, no Wasm-Python heroics. AI access is one OpenAI-compatible client configuration; AI agents act on the tracker exclusively through the same metadata-driven MCP tools humans' clients use — one metadata registry, one event stream, one tool layer.
